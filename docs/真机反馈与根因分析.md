## 七、已实现：被点名消息的时效上限（过期就 drop）

配置项 **`addressed_max_age_seconds`**（默认 180 秒，0 = 关闭），在闸门判定链里排在
「静默名单」之后、「睡眠排队」之前：

- 被 @ / 私聊 的消息，如果**轮到我们处理时**已经过去超过上限 → 直接 DROP（reason `stale_addressed`）。
- 关键：判据用的是**消息在平台上发出的时间**（`event.message_obj.timestamp`），
  **不是** `time.time()`。长上下文把管线拖住几分钟时，两者能差十几分钟 —— 那正是「翻旧消息重答」的来源。
- 拿不到平台时间（=0）时**不做判定**，宁可回也不要误杀。
- 排在睡眠检查之前：睡眠期也不该把一条 20 分钟前的消息排进队列、等到早上更荒唐。
- 适配器给毫秒时间戳（> 1e11）会自动换算。

## 八、群上下文注入器怎么选（内置 vs astrbot_plugin_group_context_flow）

两者的**注入格式几乎一样**（都带昵称与时刻）：

| | 内置 `group_chat_context` | `astrbot_plugin_group_context_flow` |
|---|---|---|
| 格式 | `[昵称/注入时刻]: 内容`（`group_chat_context.py:199-201`） | `[昵称/消息时刻]: 内容` |
| 存储 | **内存**，重启即丢 | **落盘** `plugin_data/`，重启保留 |
| 增量控制 | 注入后清空队列 | 按 `conversation.cid` 推进 cursor |
| `/reset`、`/new` | 无特别处理 | 推进边界，不回灌旧消息 |
| 上限开关 | 只有条数窗口 | `max_delta_messages`（默认 0 = 不限量） |
| 诊断 | 无 | `/gflow_status`、`/gflow_clear` |
| 维护方 | AstrBot 官方 | 第三方（Tsukumi233，v0.2.2） |

**推荐：保留 flow 插件、关掉内置注入（`group_icl_enable=false`）。** 理由：

1. **不影响本插件的插话**：`builtin_stars/astrbot/main.py:145`
   `group_context_enabled = group_icl_enable or active_reply["enable"]` ——
   `active_reply.enable` 为 true 就够了，我们改写的 `possibility_reply` 走的是那条分支。
2. 落盘持久化：这台机器今天重启了 6 次 AstrBot，内置那份每次清零，flow 那份还在。
3. cursor + `/reset` 边界 → 不会重复灌同一段历史。
4. 有 `max_delta_messages` 这个**我们可控的上限**（脚本会把它从 0 收到 50）。

**唯一代价**：多一个第三方插件依赖。如果更在意「少依赖」，就反过来 ——
保留内置注入、关掉 flow（`keep-builtin` 模式），代价是重启丢历史、没有 cursor。

两种模式都在 `scripts/apply_feedback_config.sh` 里：

```bash
# 看 diff（默认 keep-flow，不写盘）
bash scripts/apply_feedback_config.sh
# 保留 flow、关内置注入
bash scripts/apply_feedback_config.sh --apply
# 反过来（保留内置、关 flow 插件）
bash scripts/apply_feedback_config.sh --apply keep-builtin
```

脚本同时收敛：群历史窗口 700->150、`group_message_max_cnt` 1000->200、
`reply_with_quote` 关、`segmented_reply.words_count_threshold` 400->2000；
写入前自动备份（`*.bak_feedback_<时间戳>`），写完重启 AstrBot。

## 九、「回复一个比一个慢」的真凶：会话历史里的内联图片

**不是上下文注入**（注入已压到 50 条上限）。实测 `conversations.content`：

| 会话 | 历史消息 | JSON 体积 | 其中 base64 图片 | 占比 | token_usage |
|---|---:|---:|---:|---:|---:|
| 群 378525932 | 192 | 11.1 MB | 51 张 / 10.0 MB | **90%** | **210,326** |
| 群 378525932（旧） | 98 | 9.0 MB | 33 张 / 8.7 MB | **96%** | 76,362 |
| 私聊 3472782072 | 88 | 7.5 MB | 31 张 / 7.5 MB | **99%** | 44,841 |
| 群 172235421 | 68 | 5.7 MB | 17 张 / 5.5 MB | **95%** | 62,048 |

AstrBot 把群里的图片**以 base64 内联存进 conversation.history**（不是引用路径），
于是每张图约 300 KB 的文字化数据永久留在历史里，**每轮请求都要重发一遍**。
现在还能 0.8~1.7 秒，是因为命中了模型侧的 prompt cache（`token_input_cached` 一度 6.7 万）；
缓存一失效（换 provider、改人设、超时）就会立刻卡住。

### 为什么压不下来：两道闸都关着

```python
# core/agent/context/manager.py:60-76
if self.config.enforce_max_turns != -1:      # 轮次截断
    result = self.truncator.truncate_by_turns(...)
if self.config.max_context_tokens > 0:        # token 压缩
    if self.compressor.should_compress(...)
```
原配置 `max_turns = -1`（**第一道完全关闭**）+ `fallback_max_tokens = 128000`
（**第二道要 12.8 万 token 才触发**）→ 历史无上限增长。

`truncate_by_turns` 语义（`core/agent/context/truncator.py:100-144`）：
**轮 = 一问一答**；`keep_most_recent_turns` 是保留上限，超过就一次丢 `drop_turns` 轮
（滞回，避免每轮都裁剪）。

### 已应用的改动

| 字段 | 原值 | 现值 | 作用 |
|---|---:|---:|---|
| `agent_runner.config.compression.max_turns` | -1 | **24** | 开启轮次截断：每会话最多保留最近约 19~24 轮 |
| `…compression.trim_turns` | 1 | **6** | 超限时一次丢 6 轮 |
| `…compression.fallback_max_tokens` | 128000 | **32000** | 第二道保险：超 3.2 万 token 走 LLM 压缩 |
| `…compression.keep_recent_ratio` | 0.15 | **0.3** | 压缩时保留最近 30%（该字段上限即 0.3） |

**实测效果**：改前同群单次请求合计 25,103~68,454 token；改后第一次调用 **13,226**。
注意：DB 里 `conversations.content` 的行**不会**因此缩小（截断作用于「发出去的内容」）。

### 两个坑（都会让改动看起来「没生效」）

1. **直接改磁盘文件不会更新 AstrBot 内存里的配置对象** —— 必须重启（脚本已带重启）。
2. **面板是「整份配置覆盖」语义**：2026-10-07 20:26 改完 `reply_with_quote=false` 后，
   它被写回过一次（面板里打开的旧标签页点了保存，用改动前的整份配置覆盖了磁盘）。
   改完配置后不要在旧标签页里点保存；或者再跑一次脚本。

## 十、★ 最值钱的一条：「回复慢 / 回旧消息」的元凶是 `astrbot_plugin_livingmemory`

### 现象

- 群里回复间隔稳定 **70~83 秒**（`respond.stage:212` 逐条实测：70.1 / 70.8 / 71.1 / 72.4 / 73.0 / 79.0 / 82.8）
- 实测滞后案例：`21:51:28` 的消息 **`22:01:37` 才被回（+602 秒）**；另一条引用滞后 **342 秒**
- 群友原话（Funa）：**「它是在爬楼逐条补回复，结果把几十分钟前的旧消息全翻出来重答一遍，还乱艾特人。热情方向没错，但缺个时间窗，超过几分钟的消息就该跳过。」**

### 根因（每一条都有行号/日志）

1. **它每条回复白吃 60 秒**：`astrbot_plugin_livingmemory` 自己的
   `core/plugin_initializer.py:356-378 ensure_initialized(timeout=30)` 被 **两个钩子各调一次**
   —— `main.py:332`（`on_llm_request` 经 `handle_memory_recall`）与 `main.py:345`（`on_llm_response` 经 `handle_memory_reflection`）。
   ```
   21:51:01.190 [livingmemory][core.plugin_initializer:376] 等待插件初始化超时（30.0秒）  ← 请求钩子
   21:51:41.597 [livingmemory][core.plugin_initializer:376] 等待插件初始化超时（30.0秒）  ← 响应钩子
   21:51:42.699 [Core][respond.stage:212] Prepare to send - ...                        ← 才发出去
   ```
2. **它永远初始化不了**：在等 **Embedding Provider**（`plugin_initializer.py:168-184` 要求 embedding+llm 同时就绪；
   `:278-292` 靠 `context.get_all_embedding_providers()`），而 AstrBot 侧 `provider_sources: []`、插件 `embedding_provider_id: ""`

3. **「回旧消息」不是谁在回放**，是同一条 LLM 路径在消化**过期 FIFO 队列**：

4. **每次重载都会重新武装 25 分钟**：`_max_provider_attempts = 60`（`:80`）指数退避 2→30 秒，

## 十一、时效闸门的坑：`message_obj.timestamp` 是「接收时间」，不是「平台发出时间」

第九节那道 `addressed_max_age_seconds = 180` 上线后**三小时 0 次命中**。原因：

```python
# core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py:421
abm.timestamp = int(time.time())      # ← OneBot 原始 event["time"] 全程没被读取（:163 / :189 同样）
# 而且 AstrBotMessage.__init__ 本身就写了 self.timestamp = int(time.time())（astrbot_message.py:67-68）
```
于是 `age = now - sent_at ≈ 0`，`age > 180` 永不成立 → `stale_addressed` 永不产生。
**真正的平台发出时间在 `message_obj.raw_message["time"]`**（OneBot v11 事件自带，`aiocqhttp.Event` 的 MRO 是 `Event→dict→object`，`.get("time")` 可用）。

**已修正**（`life/main.py:668-720 _message_sent_at`）优先级：
```
raw_message["time"]（平台发出，秒） → message_obj.timestamp（接收时间，兜底） → 0.0
（> 1e11 视作毫秒自动换算保留）
```
验证：同一条消息，旧优先级算出 `age = 2.0s`（放行），新优先级算出 `age = 312.0s` → 正确输出
`[drop] stale_addressed … 被点名消息已过去 5.2 分钟（上限 3.0）`。

⚠️ 但要注意：**它拦不住第十节那种现象**——我们的判定在流水线入口（`waking_check/stage.py:174`），
那时消息还新；排队发生在之后的会话锁上（`internal.py:220`），回复时已过去十分钟。
**根治仍是第十节那条**（摘掉 60 秒/条的损耗）。时效闸门是第二道保险。

## 十二、延迟埋点（默认关闭）

新配置 **`debug_timing`**（bool，默认 `false`，面板「拟人 → 设置页」的 **基础闸门 tab** 里可开；页面结构见第十五节）。
开启后每条被处理的消息写一行 JSON 到 `plugin_data/life/timing.jsonl`：

| 字段 | 含义 |
|---|---|
| `t_recv` | **平台发出时间**（`raw_message["time"]`；拿不到才退化成接收时间） |
| `t_recv_wall` | 我们收到/开始处理这条事件的时间 |
| `t_gate` / `t_allow` | 闸门判定完成 / 判为放行的时间 |
| `t_decorate` / `delay` / `t_ready` | 进入装饰阶段 / 那次实际 sleep 的秒数 / 延时结束准备发送 |
| `batch` | 走了攒批时记 `{lead, wait, merged}` |
| 其它 | `umo`、`sender_id`、`kind`、`action`、`reason`、`prob`、`activity`、`message_id`、`quoted_id` |

超 2000 行或 512KB 清空重写；**所有 I/O 异常都吞掉**（绝不影响判定）；
`debug_timing=false` 时零副作用（不解析数据目录、不建文件）——有 3 个单测固化这条约束。

有了它，下一个「引用滞后 342 秒」的案例可以直接拆成：平台侧积压（`t_recv_wall - t_recv`）
/ 闸门（`t_gate - t_recv_wall`）/ 排队与 LLM（`t_decorate - t_gate`）/ 我们的延时（`delay`）/ 发送（`t_ready - t_decorate`）。

## 十四、主动开口（PROACTIVE）：设计与借鉴来源

### 借鉴来源与署名

设计与参数体系借鉴自 **[`FloranceYeh/astrbot_plugin_virtual_life`](https://github.com/FloranceYeh/astrbot_plugin_virtual_life)（GPL-3.0）**——
「为机器人维护连续的虚拟人生：长期时间表、每日日程、穿搭、当前状态与主动消息」。
我们与它同为 GPL-3.0，**只借鉴设计思路，代码全部重写**。

### 抄了什么

| # | 它的做法 | 我们的落地 |
|---|---|---|
| 1 | 一天的可打扰度档位 `blocked/low/normal/high` | 配置 DSL：`timeline = "0-8=blocked,8-10=low,10-12=normal,..."`（解析失败抛清晰异常，main 捕获后退回安全默认；未覆盖时段一律 blocked） |
| 2 | 按档位给概率 `0 / 25% / 70% / 100%` | 原样采用，**但要再乘我们自己的活跃度**：`p = 档位概率 × activity_ratio` |
| 3 | 硬闸：最小空闲、冷却、**每日预算**、未回复上限 | 原样采用：`min_idle_minutes / cooldown_minutes / daily_budget / max_unanswered` |
| 4 | 窗口抖动、分段发送、`context.send_message` | 原样采用（抖动半径 `jitter_minutes`；发送不用 `request_llm`，因为没有事件可依附） |

### 故意没抄的三处（都是真机教训）

| 没抄 | 为什么 |
|---|---|
| ❌ APScheduler | 复用我们现成的 asyncio 后台循环范式（`_flush_loop` 那一套），**不引入新依赖** |
| ❌ 「等 Provider 就绪」循环 | 见第十节：livingmemory 每条回复白等 60 秒就是这么来的。我们拿不到 provider / 调用失败 / 超时 → **记日志跳过，绝不重试、绝不阻塞**；`text_chat` 一律包 `asyncio.wait_for(timeout=llm_timeout_seconds=45)` |
| ❌ 接管 `req.prompt` 或自建回复延迟 | 「要不要回」永远归闸门（`life` 的地盘）；主动开口只负责「什么时候自己开口」 |

### 一处刻意的设计取舍：不在 gate 概率上再乘一层

`gate.base_probability.proactive`（默认 0.3）**没有**参与乘法——否则 `high` 档会变成 `1.0 × 0.3 × activity`，
等于**概率被平方**，正是 `_open_active_reply` 注释里踩过的「内置那只手二次掷骰子」坑。
主动开口这一路的**基础概率就是档位概率表**，活跃度只做乘数；`gate.py` 一行未改。
（`base_probability.proactive` 在面板上已改名为「主动开口基础概率（闸门档，当前备用）」以免混淆。）

### 实现位置与判定顺序

- 纯逻辑：`life/core/proactive.py`（不 import astrbot；时钟/rng/provider 结果全部注入）
- 接线：`life/main.py` 的后台循环（一次检查最多一条在飞的 LLM 调用）
- 配置：`proactive` 组 13 个键；面板侧边栏「主动开口」页

`should_speak` 判定顺序（每条都有独立 reason 常量，日志里直接可读）：
```
disabled → empty_session_list → not_in_session_list → sleeping → blocked_slot / probability
        → max_unanswered → daily_budget_exhausted → cooldown → insufficient_idle → allow
```

### 白名单的两种写法（以及一个平台限制）

| 写法 | 匹配方式 | 备注 |
|---|---|---|
| `aiocqhttp:GroupMessage:123456` | **精确 umo**（大小写不敏感） | 立刻生效，不需要先收到消息 |
| `123456`（裸群号 / QQ号） | 退化为「umo 最后一段相等」 | ⚠️ **必须先在该会话收到过一条消息**才进候选 |

裸 id 不是会话标识，平台又枚举不出会话，所以候选集合 =
「白名单里的完整 umo」∪「见过且命中白名单的真实会话」（`candidate_sessions`）。
这条同时修掉了一个接线 bug：原实现会把 `"123456"` 当 umo 去 `send_message`（发不出去）。

## 十五、面板页面结构（方案 A：1 个设置页 + 页内 tab）与维护约定

### 结构

页面入口按 `pages/<目录名>/index.html` 发现，**但侧边栏只给每个插件一条入口**（原因见下），所以设置类字段全塞进一个 page，用页内 tab 分板块：

| 「页面」组里的显示名 | 页面目录 | 管的键 | 键数 |
|---|---|---|---:|
| 闸门设置（基础/回话/防刷/主动/打字） | `pages/1-设置/` | 页内 5 个 tab：基础闸门 / 回话策略 / 防刷与睡眠 / 主动开口 / 打字与拟人 | 65 |
| 作息活跃度曲线 | `pages/2-作息活跃度/` | `time_weights`、`interpolate_minutes`、`weekend_multiplier`、`weekend_sleep_shift_hours` | 4 |

`1-设置` 里的 5 个 tab：

| tab | 管的键 | 键数 |
|---|---|---:|
| 基础闸门 | `enable`、`verbose_log`、`debug_timing`、`base_probability.*`、`consecutive_drop_limit`、`consecutive_drop_scope`、`silence_list`、`session_whitelist` | 10 |
| 回话策略 | `addressed_max_age_seconds`、`addressed_reply.*`、`reply_delay.*` | 10 |
| 防刷与睡眠 | `session_cooldown.*`、`sleep_queue.*`、`loop_breaker.*` | 12 |
| 主动开口 | `proactive.*` | 16 |
| 打字与拟人 | 第 5 个 tab：`segmented_jitter.*`（13）、`typing_indicator.*`（4） | 17 |

**合计 69 个叶子键（设置页 65 + 折线图页 4），每个恰好出现一次**（缺失 0 / 重复 0）。
覆盖率脚本的**页面列表不变**（仍是 `1-设置` + `2-作息活跃度` 两个页面），加 tab 只在设置页内部动。

实现要点：5 个板块的表单**一次性全部渲染进 DOM**（各自的 `<section class="tabpanel">`），切 tab 只切 `display` —— 所以切走再切回不会丢未保存的修改，保存时也天然是「按全部板块取值」。字段 DOM id 带板块前缀（`f_base__enable`、`f_proact__proactive_probability_low`、`f_typing__segmented_jitter_jitter`），取值一律走 `ctrls[path]` 表，不查全局 id。

### 框架结论：为什么不能「一页一个侧边栏项」

- 前端打包 JS 里侧边栏构建器**硬编码「一插件一条 + 只取 `pages[0]`」**（`ReadmeDialog-*.js` 里的 `Me()`）；`metadata.yaml` 的 `pages:` 字段会被后端解析，**但不参与前端序列化** → 侧边栏不会为每个 page 各生成一项。
- 页内也跳不了兄弟页：iframe `sandbox` 没有 `allow-top-navigation` / `allow-popups`，且 `asset_token` 绑定 page 名。
- 所以只能「合并成一个 page + 页内 tab」（方案 A）。

### 三条必须守住的约定

1. **每页只提交自己管的键。**
   旧版单页的 `buildPayload()` 里有段「本页不管的键原样带回」逻辑——那会导致
   「打开 A 页保存，把 B 页的值覆盖成默认」。现在设置页只遍历自己的字段表（65 个键），
   折线图页只提交它那 4 个键。
2. **改 `_conf_schema.json` 后必须重跑覆盖率断言。**
   脚本思路：递归抽 schema 的叶子键（`type: object` 且有 `items` 的继续下钻），
   再在两页 HTML 里按精确的 `path: '<键>'` 匹配归属（折线图页用它的实际写法），
   断言 `缺失 = 0 且 重复 = 0`。**别用宽泛子串匹配**——`addressed_reply.enable` 会把顶层 `enable` 误判成第二个归属。
3. **目录名用 `1-` / `2-` 前缀控制 `pages[0]`。**
   侧边栏「拟人」永远打开 `pages[0]`，后端按 `sorted(..., key=name.lower())`（Unicode 码点）排序，
   所以数字前缀最稳：`1-设置`（U+0031）< `2-作息活跃度`（U+0032）→ 默认落在设置页。
   **改目录名要连带改覆盖率脚本里的页面列表**，否则断言会失真。
   页面在「页面」组里的显示名走插件 i18n：`life/.astrbot-plugin/i18n/zh-CN.json` 里的
   `pages.<目录名>.title` / `.description`（**目录名不变，排序不受影响**）。

### 部署与生效

`scripts/deploy.sh` 是「**先 `rm -rf` 容器里的插件目录、再整份拷过去**」（`cp -r` 整个目录，所以 `.astrbot-plugin/` 这种点开头的东西也会一起带过去），所以：
- 加页面 / 删页面都会自动生效（旧的 `pages/闸门设置/`、拆出来的 4 个目录就是这么消失的）
- **配置不受影响**：调好的数值都在 `/AstrBot/data/config/life_config.json`，不在插件目录里
- 部署后**面板刷新一下（F5）**才会看到新的页面
- **i18n 的页面标题/描述是插件加载时读的**（`PluginManager._load_plugin_i18n`），改完 `zh-CN.json` 要**重载/重启插件**才生效，只按 F5 不够
