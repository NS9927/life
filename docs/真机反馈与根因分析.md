## 三、根因链（四层叠加，全在 LLM / 配置侧）

1. **上下文被灌进巨量群历史**：`provider_stats` 实测单次调用 **78,377 / 76,000+ token**。
2. **同一份历史被注入两次**（日志自己都在警告）：
   `检测到内置群聊上下文感知已启用，建议关闭以避免重复注入`。
3. **分段回复把一次回答拆成多条**：`segmented_reply = {enable: true, interval: "1.5,3.5", words_count_threshold: 400}`。
4. **回复带引用**：`reply_with_quote = true` —— 当模型答的是上下文里的旧消息时，它**引用那条旧消息**，于是看起来就是「翻旧账逐条回」。

四层叠起来 = 群里看到的「爬楼逐条补回复 + 乱艾特人 + 即时消息迟迟不回」。

## 五、建议的改动（按收益排序，全在配置/人设侧，不需要改代码）

1. **两个群上下文注入二选一，关掉 `astrbot_plugin_group_context_flow`。**
   保留内置那一份：`life` 的插话逻辑正是靠内置 `active_reply` 生效的，而 flow 插件自己都在警告重复注入。
   预期：单次请求上下文从 7~8 万 token 掉到几千 —— 回复变快、不再翻旧账、成本断崖下降。
2. **缩短注入窗口**：`group_message_history_max_cnt` 700 → **100~150**；`group_message_max_cnt` 1000 → **200**。
3. **`reply_with_quote` 改 false**（或至少不要对几十分钟前的消息加引用）—— 这条最能消除「他在翻前面的一个个回」的观感。
4. **分段回复**：`words_count_threshold` 400 → **2000**，或直接 `enable: false`；否则一次回答仍会被拆成多条。
5. **人设提示词加两条硬约束**：`只回应最新一条消息，不要逐条补答历史`、`不要主动 @ 人`。

## 六、插件侧还能做的（待机主确认）

群里两个人（Funa / 查丹科）都提了同一件事：**消息过期就 drop**。

可以加一个配置：`addressed_max_age_seconds`（默认 180 秒）——
被点名的消息如果在轮到我们处理时已经过去超过 N 分钟（被长上下文拖住、或攒批/队列延迟），直接丢弃不回。
这条能直接消灭「爬楼补回」这一类观感，改动很小（闸门加一个时间窗判定 + 配置项 + 单测）。

> 注意：它治的是「**我们这边拖久了以后再回**」；上面第三节第 1、3、4 层是**上下文和回复形态**的问题，必须在配置侧改，插件管不到。

## 七、已实现：被点名消息的时效上限（过期就 drop）

配置项 **`addressed_max_age_seconds`**（默认 180 秒，0 = 关闭），在闸门判定链里排在
「静默名单」之后、「睡眠排队」之前：

- 被 @ / 私聊 的消息，如果**轮到我们处理时**已经过去超过上限 → 直接 DROP（reason `stale_addressed`）。
- 关键：判据用的是**消息在平台上发出的时间**（`event.message_obj.timestamp`），
  **不是** `time.time()`。长上下文把管线拖住几分钟时，两者能差十几分钟 —— 那正是「翻旧消息重答」的来源。
- 拿不到平台时间（=0）时**不做判定**，宁可回也不要误杀。
- 排在睡眠检查之前：睡眠期也不该把一条 20 分钟前的消息排进队列、等到早上更荒唐。
- 适配器给毫秒时间戳（> 1e11）会自动换算。

## 八、群上下文注入器怎么选（内置 vs astrbot_plugin_group_context_flow）

两者的**注入格式几乎一样**（都带昵称与时刻）：

| | 内置 `group_chat_context` | `astrbot_plugin_group_context_flow` |
|---|---|---|
| 格式 | `[昵称/注入时刻]: 内容`（`group_chat_context.py:199-201`） | `[昵称/消息时刻]: 内容` |
| 存储 | **内存**，重启即丢 | **落盘** `plugin_data/`，重启保留 |
| 增量控制 | 注入后清空队列 | 按 `conversation.cid` 推进 cursor |
| `/reset`、`/new` | 无特别处理 | 推进边界，不回灌旧消息 |
| 上限开关 | 只有条数窗口 | `max_delta_messages`（默认 0 = 不限量） |
| 诊断 | 无 | `/gflow_status`、`/gflow_clear` |
| 维护方 | AstrBot 官方 | 第三方（Tsukumi233，v0.2.2） |

**推荐：保留 flow 插件、关掉内置注入（`group_icl_enable=false`）。** 理由：

1. **不影响本插件的插话**：`builtin_stars/astrbot/main.py:145`
   `group_context_enabled = group_icl_enable or active_reply["enable"]` ——
   `active_reply.enable` 为 true 就够了，我们改写的 `possibility_reply` 走的是那条分支。
2. 落盘持久化：这台机器今天重启了 6 次 AstrBot，内置那份每次清零，flow 那份还在。
3. cursor + `/reset` 边界 → 不会重复灌同一段历史。
4. 有 `max_delta_messages` 这个**我们可控的上限**（脚本会把它从 0 收到 50）。

**唯一代价**：多一个第三方插件依赖。如果更在意「少依赖」，就反过来 ——
保留内置注入、关掉 flow（`keep-builtin` 模式），代价是重启丢历史、没有 cursor。

两种模式都在 `scripts/apply_feedback_config.sh` 里：

```bash
# 看 diff（默认 keep-flow，不写盘）
bash scripts/apply_feedback_config.sh
# 保留 flow、关内置注入
bash scripts/apply_feedback_config.sh --apply
# 反过来（保留内置、关 flow 插件）
bash scripts/apply_feedback_config.sh --apply keep-builtin
```

脚本同时收敛：群历史窗口 700->150、`group_message_max_cnt` 1000->200、
`reply_with_quote` 关、`segmented_reply.words_count_threshold` 400->2000；
写入前自动备份（`*.bak_feedback_<时间戳>`），写完重启 AstrBot。

## 九、「回复一个比一个慢」的真凶：会话历史里的内联图片

**不是上下文注入**（注入已压到 50 条上限）。实测 `conversations.content`：

| 会话 | 历史消息 | JSON 体积 | 其中 base64 图片 | 占比 | token_usage |
|---|---:|---:|---:|---:|---:|
| 群 378525932 | 192 | 11.1 MB | 51 张 / 10.0 MB | **90%** | **210,326** |
| 群 378525932（旧） | 98 | 9.0 MB | 33 张 / 8.7 MB | **96%** | 76,362 |
| 私聊 3472782072 | 88 | 7.5 MB | 31 张 / 7.5 MB | **99%** | 44,841 |
| 群 172235421 | 68 | 5.7 MB | 17 张 / 5.5 MB | **95%** | 62,048 |

AstrBot 把群里的图片**以 base64 内联存进 conversation.history**（不是引用路径），
于是每张图约 300 KB 的文字化数据永久留在历史里，**每轮请求都要重发一遍**。
现在还能 0.8~1.7 秒，是因为命中了模型侧的 prompt cache（`token_input_cached` 一度 6.7 万）；
缓存一失效（换 provider、改人设、超时）就会立刻卡住。

### 为什么压不下来：两道闸都关着

```python
# core/agent/context/manager.py:60-76
if self.config.enforce_max_turns != -1:      # 轮次截断
    result = self.truncator.truncate_by_turns(...)
if self.config.max_context_tokens > 0:        # token 压缩
    if self.compressor.should_compress(...)
```
原配置 `max_turns = -1`（**第一道完全关闭**）+ `fallback_max_tokens = 128000`
（**第二道要 12.8 万 token 才触发**）→ 历史无上限增长。

`truncate_by_turns` 语义（`core/agent/context/truncator.py:100-144`）：
**轮 = 一问一答**；`keep_most_recent_turns` 是保留上限，超过就一次丢 `drop_turns` 轮
（滞回，避免每轮都裁剪）。

### 已应用的改动

| 字段 | 原值 | 现值 | 作用 |
|---|---:|---:|---|
| `agent_runner.config.compression.max_turns` | -1 | **24** | 开启轮次截断：每会话最多保留最近约 19~24 轮 |
| `…compression.trim_turns` | 1 | **6** | 超限时一次丢 6 轮 |
| `…compression.fallback_max_tokens` | 128000 | **32000** | 第二道保险：超 3.2 万 token 走 LLM 压缩 |
| `…compression.keep_recent_ratio` | 0.15 | **0.3** | 压缩时保留最近 30%（该字段上限即 0.3） |

**实测效果**：改前同群单次请求合计 25,103~68,454 token；改后第一次调用 **13,226**。
注意：DB 里 `conversations.content` 的行**不会**因此缩小（截断作用于「发出去的内容」）。

### 两个坑（都会让改动看起来「没生效」）

1. **直接改磁盘文件不会更新 AstrBot 内存里的配置对象** —— 必须重启（脚本已带重启）。
2. **面板是「整份配置覆盖」语义**：2026-10-07 20:26 改完 `reply_with_quote=false` 后，
   它被写回过一次（面板里打开的旧标签页点了保存，用改动前的整份配置覆盖了磁盘）。
   改完配置后不要在旧标签页里点保存；或者再跑一次脚本。
