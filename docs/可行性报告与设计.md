## 一、目标

做一个「作息闸门」：按**时段活跃度**决定机器人的消息**能不能发出去**。

活跃度语义 = **概率放行**，不是频率调节：

- 活跃度 0 → 消息不发
- 活跃度 20 → 每条消息有 20% 概率能发出去

参考作息表：

| 时段 | 活跃度 | 说明 |
|---|---:|---|
| 00:00–02:00 | 80 | 还在刷手机 |
| 02:00–08:00 | 0 | 睡了 |
| 08:00–10:00 | 10 | 刚醒，偶尔瞄一眼 |
| 10:00–12:00 | 30 | 上课/上班 |
| 12:00–14:00 | 40 | 午休 |
| 14:00–19:00 | 30 | 下午 |
| 19:00–23:00 | 80 | 晚上最活跃 |
| 23:00–00:00 | 60 | 准备睡 |

要求：切点做 ±45 分钟线性插值；周末整体 ×1.3 且睡眠时段后移。

## 二、设计语义（重要，别做错）

**概率放行只对「没人问它」的消息才像人。对「被点名」用概率 = 像坏了。**

| 消息类型 | 概率放行 | 理由 |
|---|---|---|
| 主动开口（没人问，自己找话题） | ✅ | 真人经常想找人聊然后没发 |
| 群聊插话（群里在聊，没 @ 它） | ✅ | 真人经常看完不说话 |
| **被 @ / 被私聊** | ❌ **绝不能用概率** | 真人被点名一定会回，只是可能晚回 |

### 睡眠时段（活跃度 0）单独处理

| 睡眠期收到的 | 处理 |
|---|---|
| 被 @ / 私聊 | **排队**，起床后按序补发（可带「刚看到（」口吻） |
| 群聊闲聊 | 直接丢弃（真人也不会翻回去补） |

### 统计陷阱：连续丢弃上限

活跃度 20% 时，对方连发 3 条 → 一条都不回的概率 = `0.8³ = 51%`。**私聊里非常扎眼。**

需要「连续丢弃上限」：同一会话短时间内最多丢 N 条，或「丢过一次，下一条必回」。

### 推荐公式

```text
P(发送) = 基础概率 × (时段活跃度 / 100) × 星期系数
```

| 时段活跃度 | 群聊插话 | 主动开口 | 被 @ / 私聊 |
|---:|---:|---:|---|
| 0 | 0 | 0 | 不丢，排队到早上 |
| 20 | 0.02 | 0.06 | 1.0（只加延迟） |
| 30 | 0.03 | 0.09 | 1.0 |
| 80 | 0.08 | 0.24 | 1.0 |

基准：群聊插话 0.1（= 当前 AstrBot 配置值）

## 三、可行性验证结论（核心，已带代码证据）

### ✅ 挂载点 1：动态改 `active_reply` 的概率值 —— 可行

AstrBot 自带一个完全同构的机制，就在群里非 @ 消息上：

```python
# astrbot/builtin_stars/astrbot/group_chat_context.py:112
async def need_active_reply(self, event) -> bool:
    cfg = self.cfg(event)                              # ← 每轮重读配置
    if not cfg["enable_active_reply"]:        return False
    if event.get_message_type() != GROUP_MESSAGE:      return False
    if event.is_at_or_wake_command:           return False   # ← @/唤醒词被排除
    if cfg["ar_whitelist"] and umo/group_id not in whitelist: return False
    match cfg["ar_method"]:
        case "possibility_reply":
            return random.random() < cfg["ar_possibility"]      # ← 就是概率放行
```

配置路径：`cfg["provider_ltm_settings"]["active_reply"]["possibility_reply"]`
当前值：profile `<你的 profile ID>` 里是 `enable=true, possibility_reply=0.1`

**三条证据链，说明插件可以动态控制它：**

1. **每轮重读，不是启动缓存**
   `group_chat_context.py:58` 的 `cfg()` 每次调用 `self.context.get_config(umo=event.unified_msg_origin)`

2. **返回的是同一个活对象**
   ```python
   # astrbot/core/astrbot_config_mgr.py:43 / :152
   self.confs: dict[str, AstrBotConfig] = {}      # 启动时 _load_all_configs 载一次
   def get_conf(self, umo) -> AstrBotConfig:
       conf = self.confs.get(uuid_)               # 从缓存取
       return conf                                # 同一个对象，不是拷贝
   ```

3. **改内存不落盘**
   `astrbot_config.py:33` → `class AstrBotConfig(dict)`，方法列表里**没有 `__setitem__`**（只重写了 `__getattr__/__setattr__/__delattr__`）。
   → `cfg["a"]["b"] = 1` 是纯字典写入，**不会触发 `save_config()`**，无磁盘 I/O。

### ✅ 挂载点 2：插件能跑在内置判定之前 —— 可行

- 排序规则：`star_handler.py:26` → `self._handlers.sort(key=lambda h: -h.extras_configs["priority"])`
  → **priority 数字越大越先执行**（默认 0）
- 内置那个调 `need_active_reply` 的 handler：
  ```python
  # astrbot/builtin_stars/astrbot/main.py:196
  @filter.platform_adapter_type(filter.PlatformAdapterType.ALL)   # ← 没写 priority = 0
  async def on_message(self, event): ...
      need_active = await self.group_chat_context.need_active_reply(event)   # :214
  ```

→ **插件用 `priority >= 1` 注册消息 handler，就能在它之前把当轮概率写进去。**

> ### ⚠️ 机制修正（2026-10-07 读真源码后更正，实现时必须知道）
>
> 插件 handler 在 `WakingCheckStage` 里**只是被收集**：`waking_check/stage.py:174-253`
> 把通过 filter 的 handler 塞进 `event.extras["activated_handlers"]`，**真正执行在 ProcessStage**
> （`process_stage/method/star_request.py:36-52`），而那个循环**每轮开头**就是
> `if event.is_stopped(): break`（`:37-38`，每轮结束再查一次 `:51-52`）。
>
> 所以 `stop_event()` 省 token 的真实机制是：**同一阶段内，后续 handler 和 LLM 段落一起被跳过**
> （`process_stage/stage.py:52-66` 的 agent 请求），而不是「阶段与阶段之间 break」。
>
> **结论不变**（`event.stop_event()` → LLM 一次都不调 → 0 token），但有两个实现后果：
> 1. 我们的 handler 和内置 `on_message`（priority 0）**在同一阶段按 priority 排队**，
>    所以 priority 必须大于 0 才轮得到我们先写值；
> 2. 我们 stop 之后，**后面所有 handler 都不再执行**，包括内置的群聊上下文记录逻辑。

### ✅ 挂载点 3：睡眠时段拦消息 + 排队 —— 可行

- 拦截：高优先级 handler 里 `event.stop_event()`（灵犀的封禁功能就是这么做的，有先例）
- 补发：定时任务到点后用 `yield event.request_llm(...)` 走完整 pipeline，或 `context.send_message(...)`

### ✅ 已定案（2026-10-07）：主动消息只能自研调度，路线 A 不成立

上游 / 灵犀的主动消息是**间隔驱动**（`task_scheduler.py`），不是概率驱动。
要把作息权重接进去，原本有两条路，现在有结论了：

- **路线 A（动态改它们的配置值）—— 不成立。**
  本机 18 个真实插件里的 4 种定时实现，**全部在启动期把触发配置固化**：
  - `pokepro/core/scheduler.py:19-27` 构造时 `self.cron = self.cfg.cron`，之后
    `CronTrigger.from_crontab(self.cron)`（`:37-63`）
  - `qzone_ultra/main.py:4629-4637` 把 cron 当**协程参数**传进 `_scheduled_loop`
  - `livingmemory/core/schedulers/decay_scheduler.py:302-321` 把时刻固化进实例字段
  - 只有 `steam_status_monitor_V3/.../polling_tracking.py:81-84` 每轮重算，但那是作者自觉写的，
    不是 AstrBot 提供的机制，推广不到别人的 scheduler

  改内存配置对**已注册的 trigger / 已经进入 sleep 的循环**完全无影响。
- **路线 B（自己实现主动消息调度）—— 唯一可行**，当前选择（尚未实现，见 README 待办）。

> 这与挂载点 1 不矛盾：`active_reply` 走 `need_active_reply`，**每条消息**都重读配置
> （`group_chat_context.py:58-69` 的 `cfg()`）；定时调度发生在消息之外，没有那个重读点。
>
> 另：全仓库搜索确认，**没有任何插件在改写 `provider_ltm_settings`**（唯一命中是
> `astrbot_plugin_group_context_flow/main.py:277-283` 的只读访问）。本插件是第一个这么干的，
> 所以第 4 步必须在真容器上验证。

### ⚠️ 已知限制：共享配置对象的竞态

`confs` 是按**配置档（profile）**缓存的，不是按会话。多个群共用同一个 profile 时，**它们共享同一个 config 对象**。

- 我们的 handler 写值 → 内置 handler 立即读，中间只隔一个 await
- **如果权重只跟时间有关（全局统一）→ 竞态完全无害**
- 只有做**分群不同权重**时才需要小心，可改用 monkey-patch `need_active_reply` 兜底

## 四、建议的插件架构

```text
astrbot_plugin_circadian/
├── main.py                  # 钩子注册（只做转发）
├── core/
│   ├── schedule.py          # 作息表：时段 → 权重，平滑插值，周内系数
│   ├── gate.py              # 概率闸门：基础概率 × 权重，连续丢弃计数
│   ├── queue.py             # 睡眠期消息队列 + 起床补发
│   └── delay.py             # 回复延迟（按作息，替代固定 0.5s 秒回）
├── _conf_schema.json
└── metadata.yaml
```

职责划分：

| 模块 | 干什么 |
|---|---|
| `schedule.py` | 输入 datetime → 输出 0~1 权重（含插值 + 星期系数）。纯函数，最好写单元测试 |
| `gate.py` | 输入 (消息类型, 权重, 会话历史) → 输出 放行/丢弃。维护连续丢弃计数 |
| `queue.py` | 睡眠期点名消息入队，到点补发 |
| `main.py` | 高优先级 handler：算权重 → 写 `active_reply.possibility_reply`；睡眠期 `stop_event` + 入队 |

## 八、「已读不回」闸门（防两个 bot 互刷烧 token）

### 8.1 问题

同群两个 bot（你的一只和对方的一只）会互相触发 → 无限循环烧 token。

### 8.2 原生挡不住

```python
# astrbot/core/pipeline/waking_check/stage.py:96
if self.ignore_bot_self_message and event.get_self_id() == event.get_sender_id():
    return    # ← 只挡"自己发的"，挡不住另一个 bot
```

`enable_id_white_list` / `id_whitelist` 是**命令权限**用的，不是"谁的消息我不回"。
→ **必须写插件。**

### 8.3 拦截点完美：stop_event 在 LLM 之前

流水线顺序（`astrbot/core/pipeline/stage_order.py`）：

```text
1 WakingCheckStage         ← 插件 handler 在这里被派发（waking_check/stage.py:174）
2 WhitelistCheckStage
3 SessionStatusCheckStage
4 RateLimitStage
5 ContentSafetyCheckStage
6 PreProcessStage
7 ProcessStage             ← 这里才调 LLM
8 ResultDecorateStage
9 RespondStage
```

`astrbot/core/pipeline/scheduler.py:76`：每阶段执行完检查 `event.is_stopped()`，命中就 `break`。

**结论：在第 1 阶段调 `event.stop_event()` → 第 7 阶段的 LLM 一次都不会被调用 → token 消耗为 0。**
这就是字面意义的「已读不回」：事件收到了（已读），但不进 LLM（不回）。

### 8.4 三层防护

| 层 | 规则 | 作用 |
|---|---|---|
| 1 | **静默名单**：发送者在已知 bot 名单里 → stop | 明确知道对方是 bot 时 100% 有效 |
| 2 | **循环熔断**：检测 A→B→A→B 交替模式，连续 N 轮后静默 X 分钟 | **最重要** —— 不依赖"知道谁是 bot" |
| 3 | **会话冷却**：同一会话 X 秒内已回过 N 次 → 暂时已读不回 | 兜底防刷屏 |

### 8.5 设计要点（别做成哑巴）

- **点名优先放行**：被 @ / 私聊时，循环熔断应放行（万一是真人在 @），但静默名单仍生效
- **静默要有恢复时间**，到点自动恢复，不要永久
- **必须可观测**：每次已读不回打日志（哪个会话、命中哪条规则、静默到几点），否则出问题查不出来
- **名单 / 阈值 / 时长全部配置化**

### 8.6 与作息闸门合并（推荐）

两者是同一件事：**「该不该开口」的闸门**。

- 作息闸门：按**时间**放行
- 已读不回：按**发送者 / 模式**放行
- 关系：**AND** —— 两个都放行才开口

建议**合成一个插件**，共享一个 handler、一个配置面板、一条判定链：

```text
收到消息
  → 静默名单命中？          → stop（已读不回，打日志）
  → 循环熔断中？            → stop（打日志）
  → 睡眠时段？
      ├ 被点名 / 私聊      → 入队，起床补发
      └ 群聊闲聊            → stop
  → 加权概率放行？
      ├ 通过                → 正常走 pipeline（必要时改写 active_reply 概率）
      └ 丢弃                → stop（计入连续丢弃）
```

判定顺序**从便宜到贵、从硬到软**，任何一步 stop 都省下后面全部成本。

插件名可改为 `life`（回复闸门），比 circadian 更贴切。

## 九、给新会话的一句话

> 做一个 AstrBot 插件，两个闸门合一：
> **(1) 作息闸门** —— 按**时段活跃度**概率放行消息；
> **(2) 已读不回闸门** —— 静默名单 + 循环熔断，防两个 bot 互刷烧 token。
>
> **关键发现 1**：AstrBot 的 `provider_ltm_settings.active_reply.possibility_reply` 是**每轮重读内存配置对象**的，插件可以用 `priority>=1` 的 handler 在它之前动态改写这个值 —— 零改源码实现动态闸门。
> **关键发现 2**：我们 stop 掉的不是「阶段」，而是**同一阶段里后续的 handler 和 LLM 段落** —— handler 在 WakingCheckStage 只是被收集，执行在 ProcessStage，`star_request.py:37` 每轮先查 `is_stopped()`。`event.stop_event()` → **token 消耗为 0**。
>
> **已定案**：主动消息插件的调度层**缓存配置**，路线 A 不成立 → 主动开口必须自研调度（路线 B），见第三节。
> 详见第三节（可行性）与第八节（已读不回）。
